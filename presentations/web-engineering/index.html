② How Facebook & Google Manage Cookies & Sessions

Real-world giants — see how they handle your data!

Facebook Cookies

c_user xs datr fr

c_user — identifies your account. xs — encrypted session token. datr — browser fingerprint for security. fr — ad tracking & remarketing.

Facebook Sessions

Multiple Device Sessions

Each device gets a unique session token stored in DB. Suspicious login? Facebook forces logout on ALL other devices instantly!

Google Cookies

GAPS SID HSID SSID

GAPS — persists Google Auth session. SID+HSID+SSID — cryptographically signed tokens. Access tokens are short-lived; refresh tokens live server-side.

Google Security

OAuth 2.0 + Trust Score

Google uses device fingerprinting + IP tracking for anomaly detection. A trust score system decides when to ask for re-authentication on risky logins.

How It Works

1. Each login creates a unique session token stored in DB.
2. Token links to device info (User-Agent, IP).
3. Click "Logout" → server deletes that session_id from DB.
4. Next request from that device → session invalid → forced login!

Test Your Knowledge

Let's see if you were paying attention!

1️⃣ Where is a Cookie stored?

A cookie is a small text file stored in your browser (client-side). The server sends it, but your browser keeps it!

2️⃣ Where is a Session stored?

A session is stored on the server-side. Only a tiny Session ID cookie goes to your browser — like a locker key!

3️⃣ What happens to a Session when you close the browser?

Sessions are temporary! When you close the browser, the session is destroyed. That's why you have to log in again!

4️⃣ Which Facebook cookie identifies your account?

c_user is the cookie that stores your Facebook account ID. xs is the encrypted session token, and datr tracks your browser fingerprint for security.

5️⃣ What should you ALWAYS do to a "Remember Me" token before storing in DB?

Always hash the token using bcrypt before storing in DB! Never store plaintext — if the DB leaks, the hacker can't steal sessions. Encryption can be reversed, but hashing cannot!

১. Cookie vs Session — The Fundamental Difference

Analogy: You check into a hotel. Cookie is the room key in your pocket (you carry it). Session is your info at the front desk (stored on the server).

Session Flow

২. How a Session Works — Step by Step

Step 1 — Login: You enter username + password. Server verifies and creates a unique Session ID (e.g. sess_a7f3k9x2...).

Step 2 — Cookie sent: Server puts this ID into a cookie and sends it to your browser.

Step 3 — Every subsequent request: Your browser automatically sends the Session ID back to the server.

Step 4 — Server recognizes you: Server looks up the ID in its database to identify you — no need to re-enter password.

Remember Me

৩. How "Remember Me" Works

Normal sessions end when browser closes. But checking "Remember Me" keeps you logged in for up to 30 days.

Process:

1. Server generates a strong random token (e.g., UUID)

2. Token is NOT stored directly — it's hashed with bcrypt

3. The original token lives in your browser's cookie

Two critical security flags on the cookie:

HttpOnly — JavaScript can't read this cookie, protecting against XSS attacks

Secure — Only works over HTTPS, not HTTP

Token Rotation: Every auto-login replaces the old token with a new one. If someone steals an old token, it's useless.

Device Logout

৪. Logout from Multiple Devices

How does Facebook/Google "Logout from all devices" work?

The database has a Session Table like this:

Session ID User ID Device Last Active
sess_abc...user_42Chrome/WindowsToday
sess_def...user_42Safari/iPhoneYesterday
sess_ghi...user_42Firefox/Mac3 days ago

When you click "Logout from all devices", the server runs DELETE FROM sessions WHERE user_id = 42. All session records are gone. Any subsequent request from those devices fails — instant logout everywhere.

Case Study

৫. How Big Companies Do It

Facebook Cookies:

c_user — stores your User ID

xs — encrypted session token

datr — browser fingerprint for security

Google's Approach: Google uses Trust Score in addition to tokens. If your IP suddenly changes or you log in from another country, your Trust Score drops — Google then asks for re-verification. This is built on OAuth 2.0 protocol.

Theme Storage

৬. Where to Save Dark/Light Theme?

For non-logged-in users → Use Cookie
Simple data, no need for server storage. Browser remembers the theme next time.

For logged-in users → Use Database
Syncs theme across phone, laptop, and tablet — all devices get the same preference.

Critical Rules to Remember:
1. Never store Plain Text: Always hash passwords and Remember-Me tokens with bcrypt or Argon2.
2. Don't trust Client data: Any data from the browser must be validated server-side. Client-side validation is for UX, not security.
3. Beware of Session Fixation: After successful login, invalidate the old Session ID and create a new one.

২. সেশন কীভাবে কাজ করে?

ধাপ ১ — লগইন করলে: তুমি username আর password দিলে। সার্ভার যাচাই করে একটা ইউনিক Session ID তৈরি করে। উদাহরণ: sess_a7f3k9x2...

ধাপ ২ — কুকিতে পাঠানো হয়: সার্ভার এই ID-টা একটা কুকির মধ্যে ভরে তোমার ব্রাউজারে পাঠিয়ে দেয়।

ধাপ ৩ — পরের প্রতিটি রিকোয়েস্টে: তুমি যখনই নতুন পেজ লোড করো, ব্রাউজার স্বয়ংক্রিয়ভাবে ওই Session ID সার্ভারে পাঠায়।

ধাপ ৪ — সার্ভার চেনে: সার্ভার তার ডেটাবেস থেকে ওই ID খুঁজে বের করে বোঝে তুমি কে — তাই বারবার পাসওয়ার্ড দিতে হয় না।

রিমেম্বার মি

৩. "Remember Me" কীভাবে কাজ করে?

সাধারণ সেশন ব্রাউজার বন্ধ হলেই শেষ। কিন্তু "Remember Me" চেক করলে ৩০ দিন পর্যন্ত লগইন থাকে।

প্রক্রিয়া:

১. সার্ভার একটা শক্তিশালী র‍্যান্ডম টোকেন তৈরি করে (যেমন UUID)

২. টোকেনটা সরাসরি ডেটাবেসে রাখা হয় না — bcrypt দিয়ে হ্যাশ করে রাখা হয়

৩. আসল টোকেনটা তোমার ব্রাউজারের কুকিতে থাকে

কুকিতে দুটো বিশেষ সুরক্ষা থাকে:

HttpOnly — JavaScript এই কুকি পড়তে পারবে না, তাই XSS অ্যাটাক থেকে সুরক্ষিত

Secure — শুধুমাত্র HTTPS-এ কাজ করবে, HTTP-তে নয়

টোকেন রোটেশন: প্রতিবার অটো-লগইন হওয়ার পর পুরনো টোকেন মুছে ফেলে নতুন টোকেন তৈরি হয়। এতে কেউ পুরনো টোকেন চুরি করলেও কাজে আসবে না।

ডিভাইস লগআউট

৪. একাধিক ডিভাইস থেকে লগআউট

ফেসবুক বা গুগল কীভাবে "Logout from all devices" করে?

ডেটাবেসে একটা Session Table থাকে এরকম:

Session ID User ID Device Last Active
sess_abc...user_42Chrome/Windowsআজ
sess_def...user_42Safari/iPhoneগতকাল
sess_ghi...user_42Firefox/Mac৩ দিন আগে

তুমি "Logout from all devices" ক্লিক করলে সার্ভার DELETE FROM sessions WHERE user_id = 42 চালিয়ে সব রেকর্ড মুছে দেয়। এরপর ওই ডিভাইসগুলো থেকে কোনো রিকোয়েস্ট আসলে সার্ভার Session ID খুঁজে পায় না — ফলে সব জায়গা থেকে লগআউট হয়ে যায়।

কেস স্টাডি

৫. বড় কোম্পানিরা কীভাবে করে?

Facebook-এর কুকি:

c_user — তোমার User ID রাখে, তোমাকে চিনতে

xs — এনক্রিপ্টেড সেশন টোকেন

datr — ব্রাউজারের পরিচয় যাচাই করে নিরাপত্তার জন্য

Google-এর পদ্ধতি: Google শুধু টোকেন নয়, Trust Score ব্যবহার করে। তোমার IP হঠাৎ বদলে গেলে বা অন্য দেশ থেকে লগইন হলে Trust Score কমে যায় — তখন Google পুনরায় ভেরিফিকেশন চায়। এটি OAuth 2.0 প্রোটোকলের উপর ভিত্তি করে কাজ করে।

থিম স্টোরেজ

৬. Dark/Light থিম কোথায় সেভ করবে?

লগইন ছাড়া ইউজারের জন্য → কুকিতে রাখো
কারণ: সহজ তথ্য, সার্ভারে রাখার দরকার নেই। ব্রাউজার পরের বার খুললেও থিম মনে থাকবে।

লগইন করা ইউজারের জন্য → ডেটাবেসে রাখো
কারণ: তাহলে ফোন, ল্যাপটপ, ট্যাব — সব ডিভাইসে একই থিম পাবে।

মনে রাখার মতো গুরুত্বপূর্ণ নিয়ম:
১. কখনো Plain Text রাখবে না: ডেটাবেসে পাসওয়ার্ড বা Remember-Me টোকেন সরাসরি রাখা মানে বিপদ ডেকে আনা। সবসময় bcrypt বা Argon2 দিয়ে হ্যাশ করো।
২. Client-এর ডেটা বিশ্বাস করো না: ব্রাউজার থেকে আসা যেকোনো তথ্য সার্ভারে যাচাই করতেই হবে। Client-side validation শুধু UX-এর জন্য, security-র জন্য নয়।
৩. Session Fixation থেকে সাবধান: লগইন সফল হওয়ার পর পুরনো Session ID বাতিল করে নতুন ID তৈরি করো।
